# Игровой сервер

`@office-worms/server`, стадия S0. WebSocket-транспорт, handshake и серверные сессии
реализованы и приняты пользователем 24 октября 2026 после локальной TCP-проверки. Комнаты и симуляция будут подключены в S1; браузерный RemoteSession — в C2.
[Контракт v1](../protocol/SPEC.md), [план сервера](ROADMAP.md).

## Запуск

Из корня, Node.js 22.16+ и npm 10+:

```sh
npm ci --workspaces=false
npm run server
```

`--workspaces=false` поддерживается для Windows, где создание npm-ссылок может вернуть EPERM.
На системах с разрешёнными workspace-ссылками также подходит обычный npm ci.
Сборка использует TypeScript paths; сервер импортирует protocol по относительному пути
между соседними пакетами. ws и типы Node закреплены в package-lock.json.
В корневых devDependencies ws продублирован для установки без workspace-ссылок.
Развёртывание S0 сохраняет структуру packages/server и packages/protocol.

По умолчанию: `ws://127.0.0.1:4180/ws`, HTTP-проверка `http://127.0.0.1:4180/health`.
Сервер не раздаёт клиент; браузерный полигон запускается отдельно через npm run dev на 4173.
Создание комнат через UI появится в S1/C2.

```sh
npm run build:server
node packages/server/dist/main.js --help
npm run server -- --port 4181
```

Отдельный запуск в LAN:

```sh
npm run server -- --host 0.0.0.0 --port 4180 --origin http://192.168.1.10:4173
```

Замените 192.168.1.10 на адрес **страницы клиента**, с которой будет открыт WebSocket.
Адрес подключения игроков — `ws://<LAN-IP-сервера>:4180/ws`; 0.0.0.0 не адрес клиента.
Повторяйте --origin для нескольких разрешённых origins; флаги заменяют исходный список.
По умолчанию разрешены только http://127.0.0.1:4173 и http://localhost:4173.
Origin сравнивается точно; wildcard, opaque null и Origin с путём запрещены.
Текущий dev-сервер клиента доступен только на localhost; настройка игрового сервера сама
по себе не публикует браузерную страницу в LAN.

Для native/CLI-клиента без заголовка Origin нужен явный `--allow-no-origin`.
Присутствующий чужой Origin остаётся запрещённым даже с этим флагом.
Внешний HTTPS-хост может быть передан через createGameServer({httpServer, config});
экземпляр управляет его listen/close. TLS из CLI S0 не настраивается.

| Настройка | CLI | Переменная среды |
| --- | --- | --- |
| Адрес привязки, по умолчанию 127.0.0.1 | --host | WORMS_HOST |
| Порт, по умолчанию 4180 | --port | WORMS_PORT |
| Список origins | повторяемый --origin | WORMS_ORIGINS через запятую |
| Разрешить отсутствие Origin | --allow-no-origin | WORMS_ALLOW_NO_ORIGIN=true/false |

Флаги переопределяют переменные среды. Некорректная конфигурация/занятый порт
завершают процесс с кодом 1 и коротким сообщением. Ctrl+C/SIGTERM закрывают соединения
с кодом 1001, прекращают приём и ограничивают ожидание остановки одной секундой.

## Сессии и граница S1

Первое сообщение — hello, не позже пяти секунд:

```json
{"protocolVersion":1,"type":"hello","requestId":"hello-1","displayName":"Владимир"}
```

Сервер возвращает welcome с серверными connectionId/playerId, нормализованным именем,
serverTimeMs и лимитами. Идентичность заморожена и привязана к этому соединению;
имя не доказывает личность человека. Подмена playerId не проходит валидацию.
Модель доверия — участники доверенной LAN; Origin фильтрует браузерные страницы,
но не является учётной записью и может быть задан native-клиентом.

Токены в M2 не выдаются: согласно P0 повторное соединение получает новую личность.
Выдача/срок/хранение resume-токенов относятся к P2/S2, а не к S0.
Общие снимки и журналы не содержат секретов.

createGameServer({onRequest, onDisconnect}) даёт S1 проверенный запрос и Session
с неизменяемой identity, send и close. onRequest может вернуть Promise;
запросы соединения исполняются последовательно. Очередь комнаты/проверка членства
добавляются в S1. Синхронный onDisconnect освобождает место при закрытии соединения.
Без onRequest корректные команды после welcome получают error/not-implemented.
Это ожидаемый отказ стадии S0 до подключения комнат в S1.

Общие parseClientMessage/validateServerMessage проверяют обе границы.
Некорректный исходящий DTO не попадает в сокет: соединение закрывается 1011.
Ошибка обработчика даёт internal-error и закрывает только затронутое соединение.

## Ограничения

- Максимум 64 WebSocket-соединения, включая ещё не прошедшие hello.
- Входящее сообщение ≤4096 байт, включая суммарный размер фрагментов. Сжатие отключено.
- Только текст, RFC 6455 версия 13; masked frames/UTF-8 проверяет ws. Binary → 1003,
  неверный UTF-8 → 1007, ошибочное framing → 1002, размер → 1009.
- Общий token bucket 30/с, burst 60, включает неверные сообщения; snapshot отдельно 1/с, burst 2.
- Непрерывная перегрузка: хотя бы один отказ в каждую секунду на протяжении пяти секунд → 1008.
- Использованные requestId/commandId хранятся до разрыва; повтор → duplicate-id без обработки.
  Максимум 100000 запросов, затем resource-limit и 1008. Повтор с прежним результатом — P2.
- Очередь обработчика: ≤60 запросов вместе с выполняемым, ≤245760 байт;
  превышение даёт resource-limit и 1013. Очередь сокета ≤1048576 байт, затем 1013.
- Ping/pong каждые 30 секунд; отсутствие pong к следующей проверке освобождает соединение.

Журнал — JSON-строки с разрешёнными полями: событие, время, серверные ID, код отказа/закрытия,
адрес/порт запуска. Имена, входные кадры, токены, значения Origin и тексты исключений не пишутся.

Транспорт: [ws 8.20.0, официальный API](https://github.com/websockets/ws/blob/8.20.0/doc/ws.md).
В types/ws.d.ts описана используемая часть API; установка @types/ws не нужна.
Типы проверяются сборкой, поведение транспорта — интеграционными тестами.

## Проверки и оставшаяся приёмка

```sh
npm test
npm test --workspace=@office-worms/server
npm run test:server:tcp
```

`npm run test:server:tcp` доступна как из корня проекта, так и из packages/server.

Обычные тесты используют настоящий node:http и ws через Duplex-потоки в памяти:
HTTP Upgrade, оба WebSocket-клиента, фрагменты/UTF-8/masking, handshake, отказы,
лимиты, ID, остановка и ошибки обработчиков. Симуляция транспорта не подменяет ws.
Один тест встроенного WebSocket Node требует TCP и пропускается в обычном наборе.
`test:server:tcp` запускает те же обмены через настоящие loopback TCP-соединения,
включая встроенный клиент; детерминированный тест потокового backpressure там пропускается.

TCP-приёмка подтверждена пользователем 24 октября 2026: локальный запуск
`npm run test:server:tcp` проходит. S0 принят. В среде агента loopback-подключения
по-прежнему ограничены (EACCES); локальный результат подтверждён пользователем.
Проверка двух машин в LAN и настройки firewall остаются отдельной приёмкой S3/M5.
