# Архитектура Office Worms

Принятое разбиение от 24 октября 2026. Уточнение первого этапа:
ядро и браузерный клиент развиваются параллельно, чтобы каждую механику проверять визуально.

Один репозиторий `office-worms`, независимые npm workspace-пакеты в `packages/*`.
Позже пакеты можно выделить в отдельные репозитории.

## Продуктовые ограничения

- Обычные пошаговые Worms: разрушаемая карта, черви, перемещение, прыжок, оружие и урон.
- Цель — локальная сеть и игра во вкладке VS Code; сервер — единственный источник истины сетевого матча.
- Текущий этап — браузерный полигон без сети, два игрока за одним экраном.
- Между ходами свободное ожидание; активный таймер запускается по «Начать ход».
- Ориентир активного хода — 45–60 секунд, сейчас по умолчанию 60.
- После появления расширения оно уведомляет о наступлении очереди с настраиваемым минимальным интервалом.
- Партия может длиться час или два; в сетевой версии её не требуется постоянно держать открытой.

## Части и зоны ответственности

| Часть | Отвечает за | За её пределами |
| --- | --- | --- |
| `game-core` | Состояние матча; карта и разрушение; черви; фиксированный шаг физики; снаряды, ветер, столкновения; оружие, взрывы и урон; правила действий, очередь, таймер, победа и события | DOM, Canvas, звук, сокеты, HTTP, часы ОС, файловая система, VS Code, комнаты и авторизация |
| `protocol` | Версия протокола; сообщения и DTO; runtime-проверки; запросы/ответы и ошибки; идентификаторы команд и последовательность обновлений; форматы снимков и событий | Симуляция, серверный цикл, отображение, хранение, уведомления |
| `server` | LAN-подключения; комнаты и лобби; идентичность игроков; привязка соединения к игроку; проверка входных сообщений; последовательное применение команд; запуск ядра; публикация снимков/событий; переподключение и авторитетные часы | Дублирование физики/правил, рендеринг, интеграция с редактором |
| `client` | DOM/Canvas-отрисовка карты и сущностей, эффекты; управление и прицеливание; получение снимков/событий через сессию; показ HP, очереди и таймера; локальный адаптер для разработки | Собственная реализация физики, урона или победы; VS Code API; самостоятельные сетевые схемы в обход protocol |
| `vscode-extension` | Жизненный цикл webview; команды редактора; настройки адреса сервера и уведомлений; безопасный мост с клиентом; уведомления о ходе и ограничение частоты | Игровые правила, физика, отрисовка мира, отдельная реализация сетевого протокола |

`assets/` появится вместе с графическими/звуковыми ресурсами; ядро получает только игровые данные карты.
`docs/` хранит архитектурные решения. `scripts/` содержит локальные сборку и dev/preview-сервер;
он раздаёт статические файлы и не является игровым `server`.

## Зависимости

| Потребитель | Зависимости |
| --- | --- |
| `game-core` | Только стандартный JavaScript; никаких других частей проекта |
| `protocol` | Может импортировать публичные типы game-core через import type; DTO и проверки определяет сам |
| `server` | protocol и ws; Node.js; game-core подключается в S1 |
| `client`, локальный bootstrap | game-core для LocalSession; публичные типы и константы для отображения |
| `client`, сетевой адаптер (план) | protocol; получает состояние сервера вместо запуска локальной симуляции |
| `vscode-extension` (план) | Собранный client, контракт моста и типы protocol |

Runtime-зависимость браузерного bootstrap от ядра — намеренное решение для отладочного этапа.
Она не делает клиент авторитетным участником будущей сетевой партии.
Ядро не зависит от клиента или адаптеров; циклов нет.

## Текущий локальный поток

1. main.ts создаёт LocalSession, передав createGame/dispatch/step.
2. mountGame создаёт UI; действия пользователя уходят в GameSession.send.
3. LocalSession применяет dispatch, сохраняет состояние и публикует снимок/события подписчикам.
4. Браузерный requestAnimationFrame передаёт прошедшее время в локальный адаптер.
5. Адаптер вызывает step целое число раз с фиксированным шагом 1/60 секунды.
6. UI отображает очередь/HP/таймер; renderer рисует bitmap и готовые позиции,
   а события использует для эффектов и журнала.

Публичный клиентский вход — `mountGame(root, session, debug?)`.
Интерфейс `GameSession` отделяет UI от источника состояния.
Сейчас send синхронный; перед сетью контракт нужно дополнить асинхронными подтверждениями,
ошибками транспорта и состоянием подключения. DebugControls необязателен и нужен только полигону.
Две карты в scenarios.ts — тестовые входные данные для ядра; физика в клиент не дублируется.

## Планируемый сетевой поток

1. Клиент отправляет команду серверу по контракту protocol.
2. Сервер проверяет версию, структуру, принадлежность игрока и порядок команд.
3. Сервер вызывает dispatch(state, action) и сохраняет принятый результат.
4. Серверные часы вызывают step для активного хода и разрешения выстрела с частотой 60 Гц.
5. Снимки/события доставляются через сетевой адаптер GameSession и отображаются тем же клиентом.
6. В расширение передаётся turn-ready для уведомлений с учётом настроек.

Типы TypeScript не проверяют данные из сети. Runtime-валидация принадлежит protocol,
сервер вызывает её до ядра. Ядро дополнительно проверяет игровые условия.
playerId из сообщения не доказывает личность: его определяет сервер по соединению.
В локальном режиме авторизации нет, текущий активный игрок выбирается самим полигоном.

Начальное состояние уже содержит первого ожидающего игрока. После подключения очередь
читается из снимка; одноразовое событие могло быть пропущено.
События служат эффектам, снимок — восстановлению после переподключения.

## Время и воспроизводимость

- Ядро не вызывает часы, callbacks, таймеры, I/O, Date.now или Math.random.
- createGame, dispatch и step синхронны; входное состояние не изменяется.
- step всегда означает 1/60 секунды. В waiting/finished он ничего не продвигает.
- Во время resolving игровые действия закрыты до исчезновения снаряда и завершения падений.
- LocalSession — отладочные часы: пауза, один тик, замедление; скрытая вкладка останавливает симуляцию.
  Один кадр догоняет не более 250 мс, чтобы подвисание не создавало длинную блокировку UI.
- В сетевом режиме время считает сервер; скрытие клиента и локальная пауза на матч не влияют.
- Одинаковые входы и порядок команд/шагов дают одинаковый результат в проверенной среде JavaScript.
  Побитовая идентичность между всеми движками не гарантируется.
- Ветер задаётся при создании. При появлении seed-генерации seed должен храниться в состоянии.

## Сборка и перенос в VS Code

Сборка последовательно компилирует game-core → protocol → server → client. protocol выпускает ESM/.d.ts,
не имеет runtime-импортов ядра/платформы; его статические проверки используют обе стороны сети.
Ошибки возвращаются значениями, без исключений. Сервер S0 применяет handshake, дедупликацию ID,
rate limiting и Origin-проверки. Авторизация в комнате и игровые правила подключаются в S1.
Сервер использует относительный импорт собранного protocol для режима без workspace-ссылок;
протокол не зависит от ws/Node. Токены восстановления относятся к P2/S2.

TypeScript 5.9.2 собирает game-core и client. Скрипт build копирует статические ресурсы
и сборку ядра в packages/client/dist/core. Browser import map разрешает имя пакета в этот каталог.
Для type-checking используется paths к декларациям ядра, поэтому сборка не требует workspace-ссылок.
Bundler и зависимости браузерного runtime пока не нужны.

Браузерная оболочка — public/index.html и main.ts. Отрисовка/UI не используют VS Code API.
Для webview сохраняются mountGame и renderer; добавляются bootstrap с URI ресурсов и CSP/nonce,
сетевой адаптер и мост к расширению. Само расширение пока не создано.
Подробный план и ограничения: [документация клиента](../packages/client/README.md).

## Следующие этапы

Подробный [план проекта](roadmap.md) фиксирует вехи интеграции, зависимости и критерии LAN MVP.
В каждом из пяти подпроектов есть ROADMAP.md с этапами и критериями готовности.

1. Развивать ядро и клиент вместе: ходьба/прыжок, столкновения червей, отбрасывание, урон от падения.
2. Подключить готовый protocol к сетевому адаптеру и минимальному авторитетному серверу.
3. Встроить клиент в webview, добавить уведомления, переподключение и ограничения частоты.
4. Развивать оружие, команды из нескольких червей и карты.

Полный MVP сохраняет цель: два игрока, по одному червю на команду, одно поле,
ходьба, прыжок, базука с углом/силой, разрушение, урон, очередь и победа.

## Открытые решения

WebSocket /ws, версия, лобби и лимиты зафиксированы в [спецификации P0](../packages/protocol/SPEC.md).
Формат дельт карты, хранение партий, discovery сервера, восстановление после его перезапуска,
пределы комнат/игроков и политика отключившегося активного игрока ещё не определены.
WebSocket выбран для игры; текущее SSE-соединение нужно только live reload dev-сервера.
